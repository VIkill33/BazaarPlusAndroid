# Android 专用启动器方案

日期：2026-10-22。状态：历史提案，已进入实施；当前行为以 [Android README](../README.md)、
[架构决策](adr/0001-dedicated-launcher.md)与[真机记录](device-validation.md)为准。

本文保留实施前的单 APK 启动器产品与技术方案；文中的未来验收要求不代表已经通过。
正式采用的架构决策见上述 ADR，自动更新仍未提供。

## 1. 目标与范围

基于 FusionCore 源码制作 BazaarPlusPlus 专用启动器，将加载器、Android 插件和初始化引导集成到一个 APK。用户无需电脑、ADB、手动复制 DLL 或安装开发工具。

首次使用的目标流程为：安装正版游戏 → 安装启动器 → 完成系统授权 → 点击初始化 → 首次登录 → 进入游戏。日常使用只需打开启动器并点击「启动游戏」。

首版面向小范围测试，采用「APK 内置运行框架与插件，首次联网补齐匹配依赖」的方式。不承诺完全离线初始化、自动登录或所有设备兼容。

本方案不增加回放、历史、上传等尚未移植的游戏内功能；插件能力及验收边界继续以[功能清单](feature-checklist.md)和[真机验证记录](device-validation.md)为准。

## 2. 现有基础与待验证假设

| 项目 | 当前依据 | 对启动器的含义 |
|---|---|---|
| 加载器基线 | [toolchain.json](../toolchain.json) 固定来源和校验值 | 首版沿用已验证基线，不自动追随上游最新版 |
| 框架初始化 | FusionCore 的 `BootstrapActivity.prepareConfig` 已包含资源复制、Unity 版本识别、依赖准备和运行时解压 | 在现有流程上增加编排、校验和恢复，不另造加载器 |
| 游戏识别与授权 | FusionCore 的 `SelectorActivity` 已有已安装游戏识别及授权流程 | 收敛为指定游戏的中文引导 |
| 插件产物 | `build_probe.py` 生成 DLL 和 `artifacts/mod/build-inputs.json` | 将经过验收的 DLL 与校验信息作为构建输入 |
| 构筑数据 | 插件项目已嵌入快照，见 [data/README.md](../data/README.md) | 无需让用户单独安装构筑数据 |
| 代理程序集 | 当前使用目标手机版生成的 IL2CPP 代理编译 | 新设备仍需生成其运行环境所需代理，不能直接分发测试手机的代理目录 |

现有设备上的成功运行不能证明重新签名、独立应用 ID 的定制 APK 也能运行。新 APK 的登录、代理生成、游戏启动及更新均需重新验收。

## 3. 产品交互

### 3.1 首页

首页只展示游戏是否安装、兼容性状态、初始化状态、插件版本和一个主按钮。

| 当前状态 | 主按钮 | 辅助操作 |
|---|---|---|
| 未安装游戏 | 查看安装说明 | 重新检测 |
| 缺少必要授权 | 前往授权 | 查看用途 |
| 已识别且未初始化 | 初始化 | 查看环境 |
| 初始化中 | 显示当前步骤，防止重复执行 | 可取消步骤提供取消入口 |
| 初始化完成 | 启动游戏 | 检查环境、修复、导出诊断 |
| 游戏版本发生变化 | 检查兼容性 | 查看版本说明 |
| 初始化失败 | 重试失败步骤 | 查看原因、导出诊断 |

通用游戏列表及上游高级调试选项不作为默认入口；技术细节放在可展开的诊断页。面向用户说明「准备运行环境」「安装插件」等动作，不要求用户理解 BepInEx 或 interop。

### 3.2 首次初始化

1. 检查目标游戏包、版本、ABI、可用空间和联网条件。
2. 按当前步骤请求必要权限；返回应用后自动重新检查。
3. 读取内置发行清单，核对框架、插件及匹配规则。
4. 从用户已安装的游戏读取启动所需资源，准备加载器运行目录。
5. 下载或复用经过校验的匹配 Unity 依赖，解压内置框架和运行时。
6. 在游戏运行前安装插件，核对落盘 DLL 的 SHA-256。
7. 启动加载器，触发代理生成和插件加载；区分「文件已准备」与「插件已加载」。
8. 用户在游戏内完成首次登录和必要的游戏资源下载。

不显示虚假的总进度。已知文件长度时显示下载进度；解压、代理生成等阶段显示步骤与耗时。超时后允许诊断和重试，不因耗时较长就清除数据。

### 3.3 必须保留的用户操作

- 用户自行安装正版游戏及启动器 APK。
- 系统要求的权限和安装确认由用户完成，程序只负责解释与跳转。
- 游戏账号登录、验证码和游戏内确认由用户完成。
- 首次可能需要联网下载加载器依赖和游戏资源。

沿用当前外部共享目录时，需要引导用户开启所有文件访问权限。是否改用应用专属目录以减少权限，作为独立兼容性研究，不作为首版交付前提。

## 4. 技术结构

### 4.1 源码集成方式

维护可追溯到固定上游提交的 FusionCore 定制分支，以其 Android 工程生成单个 APK。新增专用首页、初始化协调器和插件部署模块，在现有启动链上接入。

不采用「在外层 APK 内再安装一个 FusionCore APK」的方式，否则用户仍需安装两个应用，并增加跨应用权限和数据协作。初始化逻辑使用 Android 原生代码，不依赖手机 shell、Root 或 ADB。

正式源码必须进入可版本管理的独立仓库或明确的源码集成目录；当前被忽略的 `artifacts/tooling/FusionCore` 仅供核查和本机构建，不能成为唯一可维护源码。具体仓库归属在实施前确定。

### 4.2 模块职责

下列名称为建议职责，尚无对应实现。

| 模块 | 职责 |
|---|---|
| 专用首页 | 状态展示、授权引导、启动、修复与诊断入口 |
| 环境检查 | 游戏包、版本、ABI、空间、权限及目录可写性 |
| 初始化协调器 | 阶段状态、互斥执行、失败恢复及取消 |
| 依赖管理 | 匹配依赖选择、下载、校验、缓存和解压 |
| 插件部署 | 校验内置 DLL、暂存、替换及保留上一可用版本 |
| 加载器适配 | 调用 FusionCore 启动链，关联当前启动结果 |
| 诊断模块 | 输出当前环境、阶段错误及经筛选的运行证据 |

首版尽量缩小对 FusionCore 加载核心的改动。定制代码与上游同步变更分别维护，便于定位游戏兼容性回归。

### 4.3 应用身份与签名

采用独立应用 ID、中文应用名称和自己的发布签名，避免覆盖用户原有 FusionCore。首个测试发行版即固定签名和递增的 `versionCode`，避免后续升级要求卸载。

实施前审计应用 ID、Java 类路径、JNI 查找、Manifest、文件共享配置和缓存路径的关系。当前原生代码引用 `FusionConfig`、`JniBridge` 的完整类名，不能机械全局替换包名。应用 ID 与 Java 命名空间可分别处理，以最小改动完成适配。

独立应用 ID 会建立新的应用私有环境，不自动继承原 FusionCore 的登录状态。首版不自动迁移旧环境；检测到共用外部目录时，必须先处理隔离，避免两个加载器相互覆盖。

## 5. 发行输入与数据归属

### 5.1 内置发行清单

APK 构建时生成启动器专用发行清单，至少包含：

- 清单格式版本、发行版本及源码提交。
- FusionCore 上游提交和定制源码提交。
- Android 插件版本、构建提交及 SHA-256。
- 内置框架和运行时的版本、摘要及来源。
- 支持的 ABI、游戏版本和对应依赖映射。
- 外部依赖的下载位置、大小与 SHA-256。

清单从固定工具链和经过验收的构建结果生成，避免人工维护多份版本号。当前插件的 `Plugin` 元数据版本与启动器发行版本需有明确映射，不能只依赖文件名判断更新。

启动器发行暂不直接复用桌面 Product Release；若后续纳入根发布体系，需先明确 Android 产物、消费者及发布契约。

### 5.2 文件边界

| 文件类型 | 来源与处理 |
|---|---|
| 插件 DLL、所需框架和运行时 | 构建时固定来源，内置 APK，附必要许可 |
| Unity 匹配依赖 | 首版按清单下载并校验；是否允许内置分发需逐项核查 |
| 游戏资源 | 从用户已安装游戏准备，不随启动器分发游戏 APK |
| IL2CPP 代理 | 按当前设备加载环境生成，不打包开发者手机产物 |
| 游戏账号与持久数据 | 由游戏和加载环境管理，修复不清除、不导出 |
| 日志和诊断 | 保存在本机，由用户主动导出 |

新启动器使用独立目录，避免覆盖现有手动安装环境；目录改动需覆盖配置、代理、缓存和原生启动参数的一致性。确切路径由实现配置拥有，文档不再维护一份路径常量。

## 6. 初始化可靠性

### 6.1 阶段状态

建议状态依次为：环境检查、等待授权、资源准备、依赖准备、框架准备、插件部署、等待运行时、插件已加载。任一阶段可转入失败状态，记录可重试原因。

持久化阶段记录只能用于恢复提示。恢复时重新验证游戏版本和文件摘要，不能看到「上次完成」就跳过校验。同一环境仅允许一个初始化或修复任务；界面旋转、应用退到后台和重复点击不应重复解压或启动。

### 6.2 写入与恢复

- 下载写入临时文件，校验通过后再投入使用；校验失败的文件不进入有效缓存。
- 解压到暂存目录，拒绝越界路径，验证必要文件后再切换；具体切换方案须验证 Android 文件系统行为。
- 插件仅在游戏未运行时替换；替换前保留上一可用版本，失败恢复旧版本。
- 已有有效缓存可离线复用；缺少依赖时明确说明原因，不循环重试启动。
- 上游当前存在依赖下载失败后回退原始 Unity 库的行为；专用版需按已测兼容规则决定是否允许该回退，不能把回退当作初始化成功。
- 「修复」只重建明确归属的框架、依赖缓存和插件，禁止递归删除整个游戏目录。

进程死亡后是否可安全恢复代理生成，需要专项验证。长任务是否需要前台服务，应根据实际执行位置和后台限制决定，不提前承诺退出应用后仍持续初始化。

### 6.3 加载成功证据

DLL 存在、复制成功和启动 Activity 均不足以证明插件已加载。建议为每次启动分配会话标识，增加最小握手，包含插件版本、当前会话和成功状态。

首版若通过日志判断，必须读取本次启动范围，并核对实际 DLL 校验值及 `android.mod.loaded`；不能使用旧日志或上次标记。获取不到可靠证据时显示「已启动，加载状态待确认」，不显示「插件运行正常」。

插件加载成功、游戏登录成功和游戏内各功能通过验收是不同状态，分别记录。

## 7. 兼容、更新与回退

首版兼容名单以现有[真机记录](device-validation.md)为起点，并经过专用 APK 重新验证。上游声明的 Android 最低版本不能直接作为本产品已支持范围。

每次启动比较游戏版本、Unity 版本、ABI、框架和插件组合。遇到未知游戏版本时进入待验证状态，默认不执行插件启动；后续如提供测试入口，需明确展示其未验证性质。

首版通过安装新 APK 更新启动器和内置插件，更新后自动检查并部署。APK 更新由系统安装界面确认，要求应用 ID 和签名保持一致。首版不做远程 DLL 热更新，减少版本组合。

后续自动更新再引入签名发行元数据、受信下载源、摘要校验、版本兼容判断和上一可用插件回退。摘要用于检查完整性，不能单独代替更新来源认证。不得在游戏进程运行中替换插件。

游戏版本变化时只重建失效的派生数据；不得将清除登录数据当成通用修复。旧插件不保证兼容新游戏，回退必须仍符合兼容名单。

## 8. 诊断与分发

诊断页展示游戏及插件版本、ABI、最近失败步骤、缓存校验结果和本次启动状态。导出采用白名单，仅包含必要环境信息、清单摘要、初始化日志和相关错误。

导出前过滤账号标识、令牌、聊天和无关路径；原始游戏日志可能包含敏感信息，不能直接整目录打包。首版不自动上传诊断，用户自行选择是否分享。

小范围发行提供签名 APK、SHA-256、版本说明、安装指引、已知问题和源码入口。包体不含开发探针、游戏 APK、开发设备代理、设备截图或账号数据。

FusionCore 的 GPL-3.0 许可、原项目 MIT 许可，以及内置框架、运行时和其他依赖的再分发要求需在发布前逐项落实。保留版权与许可，提供定制加载器对应源码和必要构建材料；依赖下载或内置方式不能替代许可核查。

## 9. 分阶段实施

| 阶段 | 交付内容 | 完成条件 |
|---|---|---|
| 技术验证 | 固定源码、独立应用身份、签名 APK、内置插件接入启动链 | 新身份下能初始化、登录及加载当前插件 |
| 最小可用版 | 专用首页、授权引导、进度、自动部署、失败重试 | 全新配置手机无需电脑完成首次使用 |
| 小范围测试版 | 环境修复、版本兼容检查、诊断导出、覆盖更新 | 安装、升级、失败恢复及多设备验收通过 |
| 后续增强 | 更新检查、依赖分发优化、必要的插件独立更新 | 完成来源认证、回退及更新故障验证 |

首版优先解决首次初始化与第二台设备安装，不同时扩展游戏内功能。只有已完成当前构建验收的功能进入发行说明；本文阶段不代表进度承诺。

实施前对包名/JNI、数据目录隔离、初始化恢复和更新边界进行独立评审；结论写入实施任务和相应 ADR。

## 10. 验收标准

以下均为未来验收要求，目前未执行。

| 场景 | 通过标准 |
|---|---|
| 全新安装 | 仅安装正版游戏与签名启动器，经过必要授权、登录后看到插件入口，无 ADB 或手动文件操作 |
| 新设备代理生成 | 使用该环境生成的代理成功加载插件，未复制开发设备代理 |
| 权限拒绝与撤销 | 解释缺失权限，可返回恢复，不反复弹窗或崩溃 |
| 下载失败 | 断网、超时、校验失败均有明确状态；重试不使用损坏文件 |
| 缓存命中 | 已有有效依赖时可跳过下载；游戏本身是否需要联网单独判断 |
| 空间不足 | 在可检查的步骤提前说明；中途不足时不把残缺环境标记成功 |
| 中断恢复 | 初始化中进程退出或设备重启后可恢复，不清除账号及持久数据 |
| 防重复执行 | 连点、界面重建、后台恢复不会并行部署或重复启动 |
| 已有 FusionCore | 新应用安装与运行不覆盖其插件、配置、账号及缓存 |
| APK 覆盖更新 | 同签名新版本覆盖安装成功，登录和持久数据保留，插件校验值更新 |
| 游戏更新 | 识别版本变化；未验证版本不误报兼容，不沿用失效代理 |
| 加载证据 | 当前会话、版本、DLL 摘要与加载日志对应，旧成功标记不导致误判 |
| 修复 | 可重建可恢复组件，游戏账号、持久数据和用户其他文件保持完整 |
| 诊断导出 | 用户主动触发，内容最小化，检查无令牌与账号敏感数据 |
| 游戏内回归 | 按既有功能清单验证本次插件，覆盖标准与高级输入模式 |

至少覆盖现有设备及另一台不同环境的真实 arm64 设备。记录 Android、游戏、启动器与插件版本，保存本次证据；未覆盖环境明确标为待验证。

游戏操作遵循根 `AGENTS.md` 的真机测试约束：不为初始化验收擅自购买、选择事件、推进战斗、上传或清除数据；需要新对局时仅使用休闲模式。
