# ADR-0002：Android 独立历史存储与启动器 JNI 桥

状态：M0 原生采集、存储基线与设计边界已定稿；完整历史功能尚未实现或验收。

## 决策

Android 历史采用 Java 系统 SQLite，不加载桌面 Microsoft.Data.Sqlite 或复用桌面
V6 数据库。目录由 `HistoryAccessLock.DIRECTORY_NAME` 持有，通过
`Utilities.getExternalFusionCoreDirectory` 定位当前目标游戏；初始化和修复不拥有此目录。
schema、归档和游戏版本分别管理，归档不宣称桌面兼容。

`BootstrapActivity.runBootstrapFlow` 在加载游戏前取得 `HistoryRuntime` 的游戏租约。
同一目标的游戏与维护共享 `HistoryAccessLock` 的操作系统独占文件锁；进程内路径表
在打开第二个描述符前拒绝重入，避免 POSIX 关闭任意同 inode 描述符释放原锁。
进入原生加载前的失败释放租约；开始原生加载后保留至进程死亡。Unity 可能在 Activity
销毁后继续运行，不能根据首页可见或目标独立进程不存在释放锁。维护不得删除锁文件。

JNI 由启动器自己的 `bpphistory` 库持有 JVM 和桥类全局引用。Java 装载库时解析
`HistoryEnvironment`，C# 通过有界 UTF-8 缓冲区 P/Invoke 调用；JNI 层在后台线程
按需附加 JVM、清理局部引用、传播 Java 错误并仅分离自己附加的线程。
不在后台通过 Unity AndroidJNI 代理调用 Java，也不向后台传递 Unity 或 IL2CPP 对象。

原生宿主在启动 CoreCLR 前，通过进程环境发布 ABI 版本与已初始化入口地址，C#
只将该入口转换为委托，不自行重新装载库。地址不落盘、不进入归档，不能跨进程复用。
Android 的 Java 与 CoreCLR 装载路径可能得到独立库实例；M0 已观察到直接按库名查找失败，
按绝对路径再次装载后入口存在但 JVM 状态为空。不得将第二个库实例误当作初始化成功。
环境检查请求仅接受有界 ASCII 标识；Java 返回值通过标准 UTF-8 字节数组传出，
不把 JNI Modified UTF-8 当作业务 JSON 的通用传输编码。

## 实测原因与边界

本次 M0 的临时探针在 .NET 后台线程经 Unity AndroidJNI 代理调用时出现原生
SIGSEGV（2026-10-24，Android 14，证据在忽略目录 `artifacts/history-m0/`）。
托管异常捕获无法隔离此故障，因此改用独立 JNI ABI；不保留两条桥接实现。
具体崩溃指令尚未符号化，不将故障归因到某个尚未证实的代理方法。

`HistoryEnvironment.verify` 仅在随机命名的隔离数据库验证 WAL、外键、事务回滚、
并发读取及关闭重开，不创建业务 schema，也不触碰 `history.sqlite`。
后续 M1 仍须验证跨实例初始化锁、迁移失败保留与业务单写队列。
PvP/PvE、桥压力和采集基线的实际证据见真机记录；不能据此声称完整历史功能通过。

## 原生身份与战斗窗口

`ClientCache.Profile` 可先返回全零账号 UUID，不能作为已确认身份。
账号未确认时隔离本次进程会话，确认后只归属该会话的暂存记录；确认账号改变即关闭
旧作用域的观察窗口，晚回调不能向新账号写入。真实账号切换在 M4 多账号验收，
当前只有同一登录账号，未将字段可读性当作切换验收通过。

本次真机观察中，`NetMessageRunInitialized.RunId` 在休闲局重启后保持一致。
`Data.CurrentState.CurrentEncounterId` 在 PvE 等于怪物模板 ID，在 PvP 为空，
不能作为战斗唯一身份；短 `MessageId` 也尚无跨重连稳定性证据。
`ReplayState` 会再次调用 `CombatSimHandler.Simulate`，届时天数可能已经前进。

因此战斗采用持久化本地窗口 UUID 和事务内递增的采集序号：UUID 关联原始开始与结果，
序号只提供本地排序，不伪装成服务端幂等 ID。原始调用执行前绑定窗口 UUID，任务完成
只更新这个 UUID，不按完成时当前 Run 或天数重新定位。明确白名单检查点为同一已确认
账号／Run 的 `ChoiceState`、`EncounterState`、`LootState`、`LevelUpState`；
加载、断线、空状态、未确认账号和 `ReplayState` 均不能开启新窗口。

同一进程中从明确检查点进入 `CombatState`／`PVPCombatState` 的原始模拟可开启窗口；
保存进程会话 UUID、原始 opening 事实、消息和指纹证据，结果完成后仍保留去重证据。
重复调用、重复结果、旧窗口晚到即使发生在新检查点之后，也不能创建新窗口。
同天同小时多场由各自明确窗口及持久序号区分，不按天数、小时或阵容去重。

跨进程直接恢复战斗时，同 Run、进度、阵容指纹相等或“只有一条匹配记录”都不能证明
是同一原始 opening。现有 pending 或 completed 记录均不自动续接、不覆盖、不另增一场；
将本次不确定观察隔离保存并显示“战斗身份未确认”。首次中途启用且无对应历史时可保存
独立 partial 身份及“缺少可靠 opening”标记，再次重启不得再次创建同一 partial。
新的明确检查点和原始进入可恢复后续记录；证据不足继续隔离。这允许明确缺失，不承诺
重连零丢失，也不把缺失伪装成合并成功。

该策略已通过独立只读评审；M1 仍须执行重复、晚到、跨进程歧义及硬杀恢复的行为测试。

## 首版性能预算

M0 最终样本为 9 件物品、1 个技能、280 项属性；复制快照约 14.2 ms，包含元数据、
回放判断和后台投递的完整采集入口约 27.2 ms。预热首次单卡约 40–45 ms，后续约
1–8 ms；预热放启动／恢复阶段，每次只投影一张卡，不在首次战斗集中触发全部冷路径。
这些是 Android 14 单设备样本，不是最大阵容或低配置设备的性能上限。

M1 以完整采集入口 33 ms 为目标，在卡牌／属性边界检查 50 ms 中止预算；中止必须保存
明确的部分失败状态，不能截断后标为完整。单个原生调用不能被此预算强行抢占，超时须
记录实际值。后台串行事务目标 500 ms，已接受请求含等待目标 2 s；这些是后续业务入口的
验收预算，不把 M0 隔离建库耗时当作业务写入实测。桥最多同时接受 4 个请求，满时明确
拒绝并给出可见失败，结果不能越过失败的前快照事务。M1 将这些值落实到单一配置入口，
后续文档引用该配置，不另维护数值副本。大阵容及低配置设备仍在 M4 验收。
